# agent-fleet CLI 统筹设计（管理类命令）

状态：设计中（待 architect 审 + 用户确认；本文档只设计，不实现）
日期：2026-05-24
决策前提（用户已定）：**分组命令风格**；**仅本地 CLI**（暂不做 agent 远程触发 / restart_server MCP 工具）；**先设计、后分批实现**。

## 1. 背景与目标

**现状**：`agent-fleet` CLI（入口 `fleet.cli:main`，argparse）只有 **1 个子命令 `setup`**（交互式 wizard：装 server + 生成各 agent 框架的 client 配置）。架构已有：`installers/`（manifest 驱动，`INSTALLER_REGISTRY = discover_installers()` 扫 `platforms/*/platform.toml`）、`frameworks/`（cursor/claude_code/cline/... 的 client 配置生成）、`detect.py`/`verify.py`/`smoke.py`/`wizard.py`/`macos_perm.py`。**管理类命令（restart/start/stop/status/logs/update/list/devices/uninstall）全空白**。

**痛点（本轮实战暴露）**：改了 server 代码必须重启进程才生效；重启「自己正连着的」server（win-device / mac-device）很麻烦——尤其 win-device:操作 test-win11 只能经 win-device 自身,杀它=杀掉执行重启命令的进程,detached `start_process` 是其子进程会被 job-object 连带杀(曾把 win-device 搞挂)。mac 的 `launchctl kickstart -k` 是原子操作没此问题。host 上还常有重复进程抢端口、日志难看、版本/状态不透明。

**目标**：把 `fleet` CLI 设计成一套**统一、分组、本地**的 fleet 管理 CLI,覆盖 MCP server 的完整生命周期(装/起/停/重启/状态/日志/更新/卸载/发现),用 manifest 作服务元数据 SSOT,平台差异藏在一层 `ServiceController` 后面。**核心解决重启痛点**(尤其 Windows 的"自重启"用一次性 Scheduled Task 解耦)。

**非目标(本设计明确排除)**:agent 远程触发重启 / `restart_server` MCP 工具(用户暂只要本地 CLI);浏览器自动化;改 server 工具本身。

## 2. 命令面（分组，`agent-fleet <group> <cmd>`）

```
agent-fleet
├── setup                          # 交互式安装+配置 wizard（已存在，保留为顶层入口）
├── service                        # 本地 MCP server 生命周期（按 role）
│   ├── list                       # 本机已知/已装 role + 状态摘要（装没装/在跑/端口/设备数）
│   ├── status [role | --all]      # 详细状态：running、pid、port、listening、holder、attached devices
│   ├── start    <role>
│   ├── stop     <role>
│   ├── restart  <role | --all>    # 平台感知重启（见 §4）
│   ├── update   [role | --all]    # git pull(repo) + 重启 → 加载新码
│   ├── logs     <role> [-f] [-n N]# 看/跟踪 server 日志
│   ├── install  <role...>         # 非交互装 server（复用现 installers）
│   └── uninstall <role>           # 卸 server（service + 可选 venv/config）
├── config                         # agent-client MCP 配置（复用 frameworks/）
│   ├── show     [framework]
│   └── generate [framework]       # 重新生成 client 配置
├── device                         # 已接设备（仅 multi_device role）
│   └── list [role]                # 列某 role 的已接设备
├── doctor [role]                  # 健康检查：依赖/权限/端口/设备可达（复用 verify.py + smoke.py）
└── version                        # CLI + 各已装 server 版本
```

设计要点:
- **role 选择**:位置参数为 manifest 的 `id`(如 `win-device`);`--all` = 本机已装的全部 role。单 host 多 role(test-win11 = win-device + android-device)各自管理。
- **本机感知**:CLI 跑在每台 host 上;经 `detect.py` 判本机 OS,经 manifest `host_os` + 已装探测决定本机有哪些 role。
- **`setup` 保留顶层**(它是一次性入口,不归 service);`install`/`uninstall` 放 `service` 组下(它们是对"服务"的操作)。
- 兼容:现有 `fleet setup` / `fleet --version` 不破坏。

## 3. 架构

### 3.1 `ServiceController`（平台抽象）
新增 `cli/src/fleet/service/` 包,定义抽象基类 + 三个实现:

```
ServiceController(role_meta)        # 抽象接口
  .is_installed() -> bool
  .start() / .stop() / .restart()
  .status() -> {running, pid, port, listening, ...}
  .logs(follow, lines) -> str | stream
  .install() / .uninstall()        # 可委托给现有 installers
```
- **WindowsServiceController**(Task Scheduler):task 名如 `MCP-WinDevice`;`restart` 用**一次性 Scheduled Task**(见 §4);`status` = `schtasks /Query` + `Get-NetTCPConnection -LocalPort <port>` + 进程匹配;`logs` = task 的日志文件;`start/stop` = `schtasks /Run` / `/End`。
- **MacServiceController**(launchd):label 如 `cc.metahub.mac-device`;`restart` = `launchctl kickstart -k gui/$(id -u)/<label>`(原子,安全);`status` = `launchctl list <label>` + 端口;`logs` = plist 的 `StandardOutPath`;`start/stop` = `bootstrap`/`bootout`。
- **(android 在 win/mac host 上)**:android-device 服务由所在 host 的机制托管(test-win11 = Task Scheduler `MCP-AndroidDevice`)→ 复用 Windows/Mac controller,role 不同而已。
- **ios-device 现状是手动 nohup**(非 launchd):本设计建议 `setup-ios.sh` 统一给它装 launchd agent(`cc.metahub.ios-device`),让 ServiceController 一致管理;过渡期 controller 对"manual"类型回退到 pgrep + nohup。**(待 architect/用户确认 ios 是否纳入本批 launchd 化。)**

### 3.2 manifest 扩展:`[service]` 段（服务元数据 SSOT）
现 `platform.toml` 有 `[platform]`(id/port)+`[server]`(module)+`[install]`,**无服务控制元数据**。新增:

```toml
[service]
type          = "scheduled_task"          # scheduled_task | launchd | manual
# Windows:
task_name     = "MCP-WinDevice"
# macOS:
launchd_label = "cc.metahub.mac-device"
launchd_domain = "gui"                     # gui/<uid> | system
# 通用:
log_path      = "~/Library/Logs/agent-fleet/mac-device.log"   # 平台占位,见下
server_path   = "platforms/macos/server/mac_device_mcp.py"
launch        = "..."                      # 可选:start 用的命令(已有 launch 脚本则引用)
```
- 平台差异字段可放 `[service.windows]` / `[service.macos]` 子表(类似现有 `[install.setup_script_by_os]`)。
- ServiceController 从 manifest 读这些,不在代码里硬编码 task 名/label/端口。`discover_installers()` 已扫 manifest,扩成同时给出 service 元数据。

### 3.3 复用现有
- `detect.py`(平台/host 检测)、`verify.py`+`smoke.py`(doctor)、`frameworks/`(config show/generate)、`installers/`(service install/uninstall)、`InstallContext`/manifest 发现。新代码主要是 `service/` controller 层 + argparse 分组 + status/logs/update 逻辑。

## 4. Windows 自重启机制（核心，解决痛点）

问题:`schtasks /End` + `/Run` 两步;若从 win-device 自身的 shell 跑,`End` 杀掉的正是执行命令的进程,`/Run` 没人执行。

**方案:一次性 Scheduled Task 解耦**。`service restart win-device` 在 Windows 上:
1. 动态创建一个一次性任务 `MCP-WinDevice-Restart`(`schtasks /Create /SC ONCE /ST <now+N> /TR "<End+sleep+Run 脚本>" /RL HIGHEST /F`,以交互用户身份),立即 `schtasks /Run` 触发它(或靠 /ST 定时);
2. 该任务由 **Task Scheduler 进程**执行(独立于 win-device),所以即使它 End 掉 win-device,自己仍继续把 win-device `/Run` 回来;
3. CLI 命令本身立即返回(重启在后台由 Task Scheduler 完成)。
4. 一次性任务执行完自删(或下次复用)。

这样 `fleet service restart win-device` 即使在 win-device 自己的 shell 里跑也安全(本设计虽只做本地 CLI,但这个解耦让"本地命令重启本机 server"稳健,且为将来远程触发留好底座)。

mac/android(win host)无此问题:mac 用 `kickstart -k`(原子);android(win)的 task 不是当前连接通道,普通 End+Run 即可。

**坑(实战记取,写进实现注意)**:① 重复进程抢端口(test-win11 常有 .venv + stray python 两个跑同一 server)→ `restart`/`stop` 要杀**全部**匹配该 server 的进程再起,`status` 要报告重复进程;② 一次性任务的运行身份要对(交互用户,否则杀不掉交互态进程);③ `/ST` 只到分钟粒度,用"立即 /Run 一次性任务"而非靠定时。

## 5. status / logs / update 细节
- **status**:对每个 role,聚合:service 装没装(task/agent 存在?)、进程在跑?(pid)、端口监听?(`Get-NetTCPConnection`/`lsof`)、(可选)打 `/mcp` initialize 探活、holder/设备数(可读 server 的 get_status/list_devices,需 server 在跑)。输出表格 + `--json`。
- **logs**:从 manifest `log_path` 读;`-f` 跟踪(Windows `Get-Content -Wait`、mac `tail -f`),`-n` 末 N 行。
- **update**:`git -C <repo> pull --ff-only`(repo 根从 CLI 安装位置/manifest 推断)→ 然后 `service restart <role|all>`。**注意**:git pull 网络慢/重置(国内 GitHub)要处理超时 + 清晰报错(本轮踩过);可加 `--no-restart` 只拉不重启。

## 6. 分批实现建议（落地时，本设计先不实现）
- **第一批(最痛)**:`service` 组核心 —— `restart`(含 Windows 一次性任务机制)、`status`、`list`、`update`;manifest `[service]` 段 + ServiceController(win + mac)。
- **第二批**:`logs`、`device list`、`doctor`、`service install/uninstall`(接现有 installers)、ios-device launchd 化。
- **第三批**:`config show/generate`(整理现有 frameworks 暴露成命令)、`version` 增强(各 server 版本)。
- 每批 subagent-driven + review gate;真机验证(test-win11 win+android、macmini/MacBook mac+ios)。

## 7. 风险与开放问题（请 architect + 用户定）
1. **ios-device launchd 化**是否纳入(现手动 nohup;不化则 ServiceController 要支持 manual 类型)。
2. **update 的 repo 根定位**:CLI 经 uvx 装在 site-packages,repo 在哪要可靠推断(本轮 cwd 定位踩过坑)——manifest/配置记录 repo 根?
3. **status 探活深度**:只查进程/端口(轻、不依赖 server 在跑),还是也打 MCP initialize(准、但慢)?默认轻 + `--probe` 深。
4. **分组命名**:`service` 是否合适(vs `server`/`svc`);`install`/`uninstall` 归 `service` 还是顶层。
5. **Windows 一次性任务的权限/身份**细节(交互用户 + HIGHEST)需真机验证。
6. 多 host 同名 role(win-device on test-win11 vs win-device-qjl):CLI 是纯本地(在哪台跑就管哪台),不涉及跨 host;controller-side 远程管理是后续(非本批)。

## 8. architect 审查结论与定稿增量（2026-05-24）

**结论:设计可行、架构方向正确**(命令分组对齐 gh/kubectl 惯例;ServiceController + manifest SSOT 思路对;Windows 一次性任务方向对)。以下采纳项已并入本设计为准。

### 8.1 必改(影响第一批正确性)
1. **Windows 一次性 Scheduled Task 自重启——补 5 个实现细节**(写进第一批实现注意事项):
   - **坑 A 端口等待**:`/End` 杀进程到端口释放有延迟,`/Run` 新进程可能抢在旧进程释放端口前启动→失败。restart 脚本要**轮询端口不再监听(最多 ~15s、500ms/次)后再 `/Run`**。
   - **坑 B 运行身份**:用 **`/RU currentuser`(当前登录用户 SAM 名)而非 `/RU INTERACTIVE`**(锁屏时 INTERACTIVE 解析失败→可能落到 SYSTEM 身份、杀不掉交互态进程);**不要 `/RL HIGHEST`**(非管理员账号会失败;End 同用户进程不需提权)。
   - **坑 C 重入**:`/Create /F` 覆盖时若上次一次性任务还在跑会报错→创建前检查 `MCP-*-Restart` 是否存在且运行,在跑则等/取消再建。
   - **坑 D 自删**:schtasks 命令行建的一次性任务**不会自动删**(`<DeleteExpiredTaskAfter>` 只能 XML/COM 设)→ restart 脚本末尾显式 `schtasks /Delete /TN MCP-*-Restart /F`(或接受残留、下次 `/Create /F` 覆盖)。
   - **坑 E launcher while 循环**:`_launch-win-device.ps1` 内有 while 自动重启 python。restart 必须经 `schtasks /End` 杀 **launcher**(python 作子进程连带死),**不能只 Kill python**(否则 launcher 3s 后抢先重启→重复进程)。
   - **坑 F(本地 CLI 也会遇到)**:agent 经 win-device MCP `start_process` 跑 `fleet service restart win-device` 时,该进程已在 win-device 的 Task Scheduler 身份下,一次性任务 `/RU` 身份须匹配才有权 End——真机必测此路径。
2. **`update` 的 repo 根定位 → 持久化配置**:uvx 临时运行时 `__file__` 在 cache、CWD 也不在 repo,运行时推断不可靠。**`setup` 完成时写 `<repo_root>/.fleet/config.toml`(含 `repo_root`),`update` 读它**(放 repo 根、不放 home:同机可有多 checkout)。**第一批就做**(否则 update 用不了)。
3. **`[service]` 段补字段**:除 type/task_name/launchd_label,补 **`launcher_script`**(相对 platform dir,如 `scripts/_launch-win-device.ps1`,restart/start 要它)、**`log_path`**(logs 要它);现有 `_manifest.py` 的 `server_path` 不含 launcher/log。
4. **`[service]` 用 `[service.by_os.windows]`/`[service.by_os.macos]` 子表**(对齐现有 `[install.setup_script_by_os]`):android-device 在不同 host_os 上 service 配置不同(win=`MCP-AndroidDevice`、macos 暂无),平铺字段区分不了。
   - manifest 加载向后兼容:`[service]` 可选,缺失不影响 installer;解析全用 `dict.get()` 设默认,**不能在 import 期崩**(`INSTALLER_REGISTRY` 是模块级常量);缺段时由 ServiceController 调用时友好报错。

### 8.2 建议改(完整性)
5. **`restart` 异步语义明确**(参照 `kubectl rollout restart`):Windows 上重启是一次性任务异步执行→命令**立即返回并打印 "restart scheduled via MCP-WinDevice-Restart"**,不假装同步等待。
6. **`status --json` 定 schema**:至少 `role_id / installed / running / pid(可null) / port / listening / version`;参照 `docker compose ps --json`、`pm2 list` 列(role/pid/port/status/uptime/restarts)、`systemctl status` 布局。
7. **ios-device 先做 `type=manual` 降级提示**(参照 tailscale/gh 对未完全支持平台的诚实降级:`fleet service restart ios-device` → 提示手动操作),**不混入 pgrep+nohup**(nohup 无 pid 文件、按名 pgrep 易误杀);launchd 化单独批次(涉 sudo/SMJobBless、当前无设备可测)。
8. **`setup` vs `service install` 语义差异写明**:`setup`=交互 wizard(首装);`service install`=非交互、幂等、自动化/CI 场景。避免"两个安装入口"困惑。
9. `status` 重复进程检测:`Get-NetTCPConnection` 只返回监听者一个,重复抢端口进程要另用 `Get-Process|Where Path -like *win_device_mcp*`(win)/`pgrep -a`(mac)。
10. `--all` 顺序/失败:默认串行、单个失败不阻断其余、最终非零 exit(参照 docker compose);可 `--parallel`。

### 8.3 可推迟(第三批/单独议)
11. `service enable`/`disable`(开机自启开关,schtasks /Change /DISABLE、launchctl disable)。
12. `config generate --write`(直接写框架配置文件,减少手动 paste)。
13. `doctor` 校验 manifest `[service]` 段与系统实际状态一致。

### 8.4 命令面定稿微调(基于审查)
- `install`/`uninstall` 暂留 `service` 组下(分组风格),但文档/help 明写与 `setup` 的差异(8.2#8)。
- `config generate` 默认输出到 stdout,`--write` 留待 8.3#12。
- `service status` 默认轻(进程/端口),`--probe` 打 MCP initialize(默认超时 5s、`--probe-timeout` 可覆盖)。
- 借鉴来源:systemctl(status 布局)、pm2(list 列)、docker compose(--json、--all 失败策略)、kubectl(rollout restart 异步语义)、tailscale/gh(紧凑输出、降级提示)。

### 8.5 第一批范围(定稿)
manifest `[service]` 段(+by_os 子表、向后兼容加载)+ `ServiceController`(win Task Scheduler 含一次性任务自重启、mac launchd kickstart)+ `<repo_root>/.fleet/config.toml`(setup 写)+ 命令 `service restart`(异步语义)/`service status`(轻+--probe、--json)/`service list`/`service update`(读 repo_root)。ios-device=manual 降级提示。真机验证 test-win11(win+android,**必测一次性任务完整重启循环 + currentuser 身份**)+ macmini/MacBook(mac;ios 无设备则跳过冒烟)。
